# 用 AI Character Engine 的 agent

Tomoshibi 的整段對話由
[AI Character Engine](https://github.com/weryk153/ai-character-engine) 驅動（`character_engine_agent`）：

- 對話、對話歷史、工具呼叫、看圖，都在引擎裡。
- 她對你的感覺（心情、信任、好感、關係階段）會隨互動累積。
- 她記得你講過的事，每段對話各自一份。
- 她有接下來想做的事，也有自己對你們之間的體會。

Tomoshibi 這一側只做轉接：把一輪輸入交給引擎、把引擎吐出來的字接回斷句／動作／
字幕／語音那條管線、把 MCP 工具登記給引擎。程式在
`src/open_llm_vtuber/agent/agents/character_engine_agent.py` 與
`src/open_llm_vtuber/character_engine/factory.py`。

## 需求

- Python 3.11 或 3.12（`.python-version` 是 3.12，uv 會自己下載）。
- OpenAI 相容的 LLM 端點（LM Studio、Ollama 的 `/v1`、OpenAI 相容 API）。對話由引擎
  直接呼叫模型，所以 `claude_llm` 這類不相容的 provider 不能用；選了會在啟動時
  說明原因。

## 安裝

引擎是 Tomoshibi 的一般依賴，`uv sync` 就會裝好（從 GitHub 裝，`pyproject.toml` 釘在
一個 commit）。啟動照常：

```sh
uv run run_server.py
```

改引擎本身時，可以暫時換成本機的原始碼：

```sh
uv pip install -e ../ai-character-engine
```

下一次 `uv sync` 會換回 `pyproject.toml` 釘的那一版。

## 啟用

預設就是它，不用另外設定：

```yaml
agent_config:
  conversation_agent_choice: 'character_engine_agent'
```

模型、MCP、斷句這些設定在 `agent_settings.conversation`。舊的 `conf.yaml` 寫的是
`basic_memory_agent`，開機時會自動升級一次（區塊改名、拿掉舊 agent 專屬的欄位）。

引擎沒裝好時 App 照常開啟，log 會寫明原因與做法，聊天畫面會提示去設定頁。

## 調整節奏

每一種背景工作都是一次額外的 LLM 呼叫，跟對話用同一顆模型。她在回話時背景工作
會讓路；一輪講完後先讀這一輪的情緒，其餘的一次一個。預設值是在 M4 16GB、
`qwen/qwen3.5-9b` 上量出來的；機器比較慢、或覺得回覆變慢時把數字調大，`0` 是停用。

```yaml
agent_settings:
  character_engine_agent:
    emotion_every: 1      # 每輪分析對方的情緒；決定她下一句的心情
    memory_every: 2       # 每 2 輪擷取一次記憶
    mood_every: 2         # 每 2 輪更新一次她自己的心情；空檔時的臉帶著它，隨時間慢慢淡掉
    summary_every: 0      # 摘要，預設停用
    reflection_every: 6   # 每 6 輪反思一次
    goal_every: 4         # 每 4 輪產生一次目標
    timeout_seconds: 60
    max_rebase_turns: 3   # 背景結果落後幾輪以內仍然採用（記憶不受此限）
    goal_max_age_days: 7  # 超過幾天沒更新的目標不再寫進提示
    goals_shown: 3  # 她同時放在心上的目標最多幾條（最急的優先）
    thoughts_shown: 2  # 她同時放在心上的想法最多幾條（最新的優先）
    max_history_messages: 80  # 對話最多留幾則給模型
```

## 資料放在哪裡

```
chat_history/<conf_uid>/engine/state.json       心情、信任、好感、關係階段
chat_history/<conf_uid>/engine/memory.jsonl     她記得的事（每段對話各自一份）
chat_history/<conf_uid>/engine/goals.jsonl      目標
chat_history/<conf_uid>/engine/cognition.jsonl  體會
```

狀態、目標、體會屬於角色，所有對話共用；記憶跟著對話走。要讓她重新開始，刪掉
`engine/` 資料夾。

對話紀錄仍然由 Tomoshibi 存在 `chat_history/<conf_uid>/<history_uid>.json`。引擎只在
記憶體裡留最近幾段對話；沒看過的對話會從這份紀錄接著講。

她記得對方什麼，由引擎負責：

- 記憶頁「對這段對話的記憶」顯示的、編輯的，是引擎的記憶。刪掉或改掉的那一行會從
  她讀到的內容裡拿掉。
- 她會拿到這段對話的全部記憶（預設最多 40 筆），跟最新一句有關的排前面。

她自己說過什麼（喜好、習慣、在做的事）也由引擎記：

- 引擎從她的話裡抽出來，整個角色共用、所有對話都看得到，每輪放進備註
  （`you said about yourself`）。頻率是 `self_memory_every`，長期記憶關掉時跟著關。
  長期記憶開關是每個角色各自的（記憶頁的開關、或角色檔的 `long_term_memory_enabled`）。
- 記憶頁「她自己的記憶」顯示的、編輯的，是引擎的這一份。
- 舊版留下的 `core_memory.md`、`self_memory.md` 不搬進引擎。舊的整理會把她當下說的
  話（「現在凌晨兩點半，去遠方不太方便」）記成事實，搬進來她每一輪都會照著講。

她說出口的話也由引擎把關：不重複、不講客服腔、不留只剩標點的碎片、主動開口不只是
應一聲、上一次主動開口問過問題這次就不問。主機原本那幾層過濾對這個 agent 跳過，
不然兩邊各擋一次，主機擋掉的句子引擎不知道。

## 背景工作用另一個模型

情緒、記憶、她自己說過什麼、目標、反思都是背景工作，每一項都是一次模型呼叫，預設
跟她講話用同一顆模型排隊。要讓它們改用另一個端點（例如另一台電腦上的 LM Studio），
在 `character_engine_agent` 底下填兩個值，或在設定頁「由引擎驅動對話」底下填：

```yaml
background_base_url: 'http://127.0.0.1:1235/v1'
background_model: 'qwen/qwen3.5-9b'
```

兩個都填才會用；只填一個或都空著，就跟她講話用同一顆。看圖仍然用她講話那一顆。

審核她從你的回饋學到的東西（證據審核、條件比對、投票）可以再指到第三顆更大的模型
（引擎 1.5.0 起的 `review_llm`）：本機 9B 抽候選夠用，審核卻會放過改寫，27B 才擋得住。
填 `review_base_url`／`review_model`，兩個都填才用，空著就跟背景模型同一顆。只在
`character_development` 開著時有作用。
對方的 LM Studio 只聽自己那台的 127.0.0.1 的話，先開一條 SSH 通道把它接到本機的
1235（`ServerAliveInterval` 不加的話通道會斷）：

```sh
ssh -f -N -o ServerAliveInterval=15 -L 1235:127.0.0.1:1234 <帳號>@<那台電腦>
```

## 送給模型的長相

引擎把她此刻的狀態、想起來的事、目標、體會寫成備註，放進對話裡、接在那一輪使用者
的話前面，而且只寫「之前的備註還沒講過的」。備註會留在原處，所以每一輪送出去的
提示都是上一輪的延伸，推論端的快取才用得上。系統提示只有人設與一段「備註怎麼讀」
的說明，狀態怎麼變都不會動到它。

記憶要是放在系統提示的中段，它一變，推論端就得把後半段系統提示連同整段對話重讀
一遍。寫進備註就只多讀新增的那幾行。

備註的標籤（`emotion`、`memory`、`goal`、`the user seems`、`For the next reply only`）
是引擎的，英文；那是給模型讀的，使用者看不到。記憶、目標、體會的內容用她回話的
語言寫（`player_language`／角色的 `reply_language`）。

她也會從備註知道現在的日期與時間。問她幾點時，9B 的模型有一半的機會不呼叫時間
工具而是編一個（實測 6 次裡 3 次）。

## 看圖

引擎的訊息只有文字。鏡頭、螢幕、上傳的圖會先用同一顆模型描述成兩三句話（約 3 秒），
她讀到的是描述；對話裡留的是你說的話，不留圖也不留描述。

## 目前的限制

- 看圖多一次模型呼叫，有圖的那一輪第一句話會晚約 3 秒。
- 模型不支援原生工具呼叫時沒有提示詞模式的退路。
- 兩個連線同時講話時，引擎一次只跑一輪，後到的要等前一個講完。
- 字幕翻譯也用同一顆模型，它不在「她回話時讓路」的機制裡。
## 角色成長與自主沉默（候選功能）

這版加入兩個預設關閉的設定，放在
`character_config.agent_config.agent_settings.character_engine_agent`：

```yaml
character_development: false
autonomous_silence: false
```

`character_development` 會在既有系統提示末尾說明「人設是起點，經驗形成的當前觀點
可以承接並超過起初的偏好」，不額外規定她應該更溫柔、更會吐槽或變成某種個性。
它讓新版引擎對角色說過的喜好、習慣與觀點建立修訂關係。舊觀點、替代它的新觀點，以及她說出
改變原因的原話都保留；對話使用目前仍有效的觀點。這不修改角色人設檔，也不改寫
姓名、身世或外觀。模型仍負責判斷一段話是否真的是觀點改變，不能把機制測試當成
「角色已經像人」的品質證明。

真正替換舊觀點前會再由獨立模型判讀確認；單純重述或換話題不替換，能與舊觀點
並存的新細節則新增保留。當前喜好、習慣與觀點另以資料形式放在系統提示末尾，
避免重啟後被初始人設中的偏好蓋過。原有提示前綴保持不變，但觀點更新會使該段
之後的推論快取失效，效能需與對話品質一起實測。

`autonomous_silence` 只用在私人聊天的閒置機會。角色選擇沉默時不會再問三次，
也不會留下發言或增加未回應次數。直播、遊戲與其他主動事件沿用原流程。

這兩項引擎能力尚未包含在本專案釘選的 PyPI 版本。開發測試要明確選用旁邊的引擎
checkout，不要只改 YAML 就以為已生效：

```sh
PYTHONPATH=../ai-character-engine/src .venv/bin/python scripts/compare_character_development.py --growth-only
```

對照預設使用本機 `1234` 的 Qwen3.5 9B 對話、經 SSH `1235` 通道連遠端 worker
的同款模型做自我記憶，紅莉栖的現有人設、三次獨立的完整對話。雙方使用相同設定；
為隔離本次變動，預設僅開自我記憶背景工作，`--full-background` 才使用完整背景節奏。
`--growth-only` 在六輪共同經驗之後重啟引擎，最後兩輪使用全新的對話，檢查已形成的
觀點與原因是否能由長期狀態承接，而非倚賴上一段聊天紀錄。輸出包含原始模型請求／
回應、逐輪記憶與完整並排 HTML，寫在新的評估目錄；不改動
現有聊天紀錄或啟用中的角色。採用前仍須人讀全文判斷，不能用詞頻或篇幅代替。

`--everyday` 改用書店避雨、烤焦早餐、看電影三種日常話題，不詢問角色是否改變，
也不要求產生成長。每組雙方各六輪，沿用 App 現有的短回覆設定，每兩輪執行
使用者記憶與自我記憶工作，其餘背景認知停用（除非指定 `--full-background`）。
第五輪前重啟引擎，使用相同使用者記憶範圍，但不帶入前四輪逐字紀錄。
這是固定輸入的對照，適合觀察接話及記憶承接，不能當成自由互動或長期成長證據。
日常對照保存於 `docs/superpowers/eval/2026-10-14-everyday-v1/`，使用上述逐筆確認
流程的完整版本。這輪兩版都出現不必要的建議與分析；候選版記得書店的橘貓，
但對「看到我就跑走」仍接成「跟你很熟」，早餐話題也再次變成說教。
這些結果不足以支持聊天自然度已改善，候選功能繼續維持預設關閉。

使用者否決日常對話後，又做了 `2026-10-14-casual-v1/` 的追加閒聊提示與診斷。
長提示完成第一組對照就判定不合格並停止，未完成原訂三組；新增程式與設定已撤回，
patch、模型原始請求／回應、診斷腳本仍保存在該目錄。當輪短提醒、移除重複懲罰、
簡短提示控制組及遠端同款模型重播，也未得到穩定可用的接話。
開啟思考的兩次診斷都在輸出上限內未產生最終回覆（約 81 秒與 59 秒）；這不是
正式吞吐量測試，不能據此判斷模型的一般性能。

另在 `2026-10-14-casual-note-v1/` 從新對話跑三組短提醒，每組六輪，仍出現把
「烤焦」說成「烤不熟」、憑空加入爭執等錯誤。對照側沿用 `everyday-v1` 的
成長候選，新側三組並行，並非同期重跑，不比較延遲。這一輪沒有可採用的自然度
修正；不能把新增提示、通過程式測試或記憶承接，當成聊天已改善的證據。

2026-10-14 的本地實測保留在 `docs/superpowers/eval/2026-10-14-growth-v4/`：
三組原版／候選版，每邊八輪，共 48 則回覆，第七輪開始是重啟後的新對話。
候選版第二、三組在新對話中承接了重啟前形成的偏好；但背景模型仍曾把相容的
觀點或含糊的重述誤當成替換。因此完整對照後又補上「逐筆、先單獨比較新舊意思」
的確認流程，用四個實際錯誤提案重播及一個合成正例檢查。這些最後修正沒有重跑
全部對話；HTML 附錄分開展示其原始提案、確認結果與全部模型請求／回應。
目前仍是未啟用的候選功能，也未驗證完整背景認知、語音、表情或遊戲中的效果。

## 從相處經驗學習（開發候選）

引擎新增 `interaction` 背景工作，讀取角色上一句實際發言與這一輪對方的回饋，
提出有原文依據的相處理解。協調器檢查引文、來源事件及使用者範圍後才保存。
同一議題可以累積多次經驗，也可以被後來的明確回饋修正；舊的經驗仍保留。
這些理解放在既有提示末尾，是可修正的解讀，不能當作固定反應規則或世界事實。
月白的人設只留下三段初始性格，沒有把這些經驗回寫進 YAML。

設定仍位於 `character_config.agent_config.agent_settings.character_engine_agent`：

```yaml
character_development: true
interaction_every: 1
interaction_topics_shown: 4
interaction_user_id: local-owner
```

`interaction_user_id` 是此單一使用者安裝的固定識別，預設留空。由主機提供，不能
從稱呼、聊天文字或歷史檔名推測；換聊天視窗時保留，換使用者時必須更換。直播、
多人對話、未指定識別或關閉長期記憶時不讀寫這份相處經驗。這不是多使用者登入
系統；共用同一安裝且需要分人時，宿主必須先接入可靠的身分來源。

資料沿用角色的引擎記憶 JSONL，scope 為角色識別加使用者識別的 SHA-256。
原文及原始識別仍存在記錄中，雜湊不是匿名化。引擎提供
`interaction_experiences(user_id)` 檢視，以及
`forget_interaction_experiences(user_id, record_ids)` 撤回指定理解。這些資料
獨立於逐字聊天歷史，重啟、新對話可承接；不會帶給另一個使用者識別。

引擎 1.4.0（2026-10-15 發行）起內建此能力與 v3e 審核，專案已釘此版；仍未預設啟用。
要測未發行的引擎改動時，明確選用旁邊的引擎 checkout：

```sh
PYTHONPATH=../ai-character-engine/src .venv/bin/python scripts/compare_interaction_learning.py
```

腳本使用月白、現有 Qwen3.5-9B 與 1234／1235 端點，三組雙邊各九輪完整對照。
雙方採同一份初始人設，僅切換相處學習；第七輪前重啟並開新對話，第九輪換人。
所有資料寫入隔離測試目錄，保留完整請求、回應、記憶及並排 HTML。
引擎替身測試只證明機制；模型是否理解正確、對話是否自然，要另讀完整結果。

修正版對照可重跑為新的目錄，或明確沿用同人設、同設定的原版完整對話：

```sh
PYTHONPATH=../ai-character-engine/src .venv/bin/python scripts/compare_interaction_learning.py \
  --out docs/superpowers/eval/my-interaction-run \
  --baseline-from docs/superpowers/eval/2026-10-14-interaction-v1
```

若之後要在 App 開發環境驗證，先於上述設定區塊明確啟用並填入私人使用者識別，
再從專案根目錄執行 `PYTHONPATH=../ai-character-engine/src .venv/bin/python run_server.py`。
本次沒有改動正在使用的 `conf.yaml`、安裝版引擎或正在執行的服務。

此次三組完整閱讀紀錄保存在
`docs/superpowers/eval/2026-10-14-interaction-v1/` 與 `2026-10-14-interaction-v2/`，
各有 `comparison.html`、`assessment.md` 及模型原始請求／回應。修正版重啟後
記得允許的稱呼，但仍混淆雙方名字、推論不存在的感受，日常對話也會無端轉題。
因此目前的結論是**機制驗證通過，模型品質未通過**，繼續維持預設關閉。

後續修正加入「解讀確認」：抽取完成後，再以同一背景模型的一次獨立呼叫檢查
使用者原話是否支持該理解，這次不帶角色人設。除了引文存在，還必須確認說話者、
感受／意圖有無依據、許可範圍及修訂關係。若回饋摘要與其餘檢查通過，但延伸教訓
沒有依據，就只保留已確認的回饋摘要；被拒絕的教訓只留在查核資料，不進入提示。
必要檢查否定、不確定、格式錯誤或逾時都不寫入。
協調器要求確認結果對應同一份提案與回饋，保存確認紀錄；舊版未確認的理解
仍能查閱及撤回，但不再進入提示，也不作為後續學習的既有主題。
每個有效候選會多一次背景呼叫；這是證據檢查，不能保證同一模型一定判斷正確。
